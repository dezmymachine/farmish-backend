# Frontend phases F0–F9 (repo `../farmish-frontend`)

**Timing:** F0–F2 may start once backend Phase 12 is done; F3 onwards after Phase 22 freezes the contract. Plan and ADR updates are committed in the **backend** repo (this `docs/` folder); code goes in the frontend repo. The same workflow applies (`AGENTS.md`): one phase per task, `pnpm ci` (defined in F0) green, and a review packet in `farmish-backend/docs/reviews/frontend-FN.md`.

## Stack (verify the latest stable versions at F0 and pin them)

- **Framework:** TanStack Start (React, file-based routing, SSR) with TanStack Router + TanStack Query. TypeScript `strict: true`, `noUncheckedIndexedAccess: true`.
- **Styling:** Tailwind CSS v4 + shadcn/ui (Radix). Icons: lucide-react. Forms: react-hook-form + zod.
- **API client:** `openapi-typescript` (types generated from `api/openapi.yaml`) + `openapi-fetch`. There are **no hand-written API types**.
- **Auth:** Firebase JS SDK (Auth + App Check). Payments: redirect to Paystack's `authorizationUrl` (Paystack Inline is optional, later).
- **Tooling:** pnpm; ESLint (typescript-eslint strict) + Prettier, or Biome (**decide in F0**); Vitest + Testing Library; Playwright for e2e; MSW for API mocking in component tests.

## Structure

```
src/
  routes/                 file-based routes (TanStack Start)
  api/
    schema.d.ts           GENERATED by `pnpm gen:api` (never edit)
    client.ts             openapi-fetch client: base URL, auth header, error normalisation
    queries/<domain>.ts   TanStack Query hooks per domain (useListings, useCheckout, ...)
  auth/                   Firebase init, AuthProvider, useAuth, route guards
  components/ui/          shadcn components
  components/<domain>/    feature components
  lib/money.ts            formatMoney(Money) → "GH₵ 12.50" via Intl.NumberFormat('en-GH', {style:'currency', currency:'GHS'})
  lib/errors.ts           ApiError from the error envelope; code → user message map
  lib/phone.ts            Ghana phone normalise/format (mirror of backend geo)
tests/e2e/                Playwright
```

## Cross-cutting rules

- **Money:** always `Money` from the API. Display with `formatMoney`. **Never** do arithmetic on money in the UI beyond display. Totals come from the API quote.
- **Errors:** every API error is `{error: {code, message, details}}`. Map `code` to friendly copy in `lib/errors.ts`. Show field `details` on forms (the `field` is the camelCase name or a JSON pointer). Handle `unauthorized` (refresh the token once, then send to sign-in), `reauth_required` (open the re-auth dialog), `rate_limited` (honour `Retry-After`) and `turnstile_failed` (reset the widget).
- **Auth header:** `Authorization: Bearer <await user.getIdToken()>` on every call. Firebase refreshes tokens itself.
- **Accessibility:** WCAG 2.1 AA. Every interactive element is keyboard-reachable with a visible focus ring. Test with `@axe-core/playwright` on key pages.
- **Performance:** mobile-first (most users are on low-end Android over 3G/4G). Keep the route-level JS budget ≤ 170 KB gzipped, serve images through the R2 CDN with `width` hints, and lazy-load below-the-fold content.
- **Security:** never store tokens in localStorage manually (Firebase handles persistence), no `dangerouslySetInnerHTML`, CSP headers at the host.

## Phases

### F0: Scaffold

- **Deliverables:** TanStack Start app, TS strict, Tailwind v4 + shadcn init, lint/format, Vitest, Playwright, `pnpm ci` (`typecheck + lint + test + build + e2e smoke`), a `.env.example` (`VITE_API_BASE_URL`, Firebase web config, `VITE_TURNSTILE_SITE_KEY`, `VITE_PAYSTACK_PUBLIC_KEY`), the `AGENTS.md` pointer, and an ADR choosing the **deploy target** (recommendation: Cloudflare Workers/Pages, already in our Cloudflare stack; confirm TanStack Start adapter support).
- **Done when:** `pnpm ci` is green, and the home page renders SSR with a health badge calling `/healthz`.

### F1: API client

- **Deliverables:**
  - `pnpm gen:api` reads `../farmish-backend/api/openapi.yaml` (dev) or the tagged release file (CI) → `schema.d.ts`
  - `client.ts` with auth middleware and error normalisation into `ApiError`
  - `lib/money.ts`, `lib/errors.ts`
  - a drift check in CI (regenerate + `git diff --exit-code`)
- **Tests:** `formatMoney` (0, 1, 100, 1250, 100000000 pesewas), error normalisation, and the auth header being attached (MSW).

### F2: Auth

- **Pages:** `/sign-in` (Google, email/password, **phone**: `signInWithPhoneNumber` + invisible `RecaptchaVerifier`, OTP input), `/sign-up`, `/account` (GET/PATCH `/v1/me`).
- **Behaviour:** an `AuthProvider` with session persistence, route guards (`requireAuth`, `requireAdmin` from `/v1/me.role`), and a re-auth dialog for `reauth_required` (phone users: `reauthenticateWithPhoneNumber`; others: their provider). App Check is initialised.
- **Tests:** guard redirects; a Playwright sign-in flow against the **Firebase Auth emulator** (email and phone test numbers).

### F3: Browse

- **Pages:** `/` (featured = diamond/enterprise promoted, categories grid, newest), `/c/$slug` (category listing with filters), `/search` (q, region, district, price range, item state, sort; URL-synced state), `/l/$slug` (detail: gallery, attributes, seller card with the verified badge and rating, the contact button calling `POST /contact` when signed in, favourite toggle, reviews).
- **Tests:** filters ↔ URL, empty states, a detail page with no PII fields rendered (assert the absence of phone unless revealed), axe checks.

### F4: Sell

- **Pages:** `/sell/onboarding` (seller profile form, region/district from `/v1/locations`), `/sell/listings` (my listings with status tabs and actions: publish/renew/mark-sold/archive), `/sell/listings/new` and `/$id/edit`.
  - The edit page has a **category-driven form**: item states, units and attributes from `/v1/categories/{slug}`. Required attributes are enforced client-side too.
  - Image upload: request `upload-url`, then `PUT` to R2 with the exact headers and a progress bar. Max 10, 5 MB, jpeg/png/webp; client-side compression to ≤ 1600 px is recommended.
- **Tests:** attribute form rendering per type, upload flow with MSW + a fake PUT, validation messages from the API `details`.

### F5: Checkout

- **Pages:**
  - `/cart`: local cart state (localStorage is fine for cart **lines only**: listing id + qty)
  - `/checkout`: delivery details per seller, then `POST /v1/checkout/quote` to show the itemised totals and the **processing fee line** (non-refundable note), then `POST /v1/checkout` with an `Idempotency-Key` generated once per attempt and kept across retries, then redirect to `authorizationUrl`
  - `/payment/callback?reference=`: poll `GET /v1/checkouts/{id}` or `GET /v1/payments/{reference}` until paid, failed or expired
- **Tests:** a double-submit sends one idempotency key; the quote display matches the API exactly (no client math); the callback page states.

### F6: Orders

- **Pages:** `/orders` (buyer), `/orders/$id` (timeline from events; cancel, confirm receipt, dispute form), `/sell/orders` (seller queue: accept, reject with reason, ship with tracking ref, mark delivered).
- **Rules:** buttons appear only for transitions legal for the current state and role, mirroring DOMAIN §4. The UI still handles a 409 gracefully.
- **Tests:** action visibility matrix per status and role; a dispute form with validation.

### F7: Payouts

- **Pages:** `/sell/payouts`: balance cards (available, in escrow, in flight, paid out), payout history, and the payout account form (type → bank list → number; step-up re-auth before submit, handling `reauth_required`; the resolved account name is shown; cooldown banner).
- **Tests:** the account number is never shown unmasked after save; the step-up flow.

### F8: Engagement

- **Deliverables:** messaging (inbox, thread with cursor pagination, unread badges, polling every 20s or SSE later); reviews (after completion); favourites page; the report dialog; supply requests (form with an items repeater, list, detail timeline, cancel); promotions (packages page with the processing-fee breakdown, buy → Paystack, then apply to a listing with the extend/upgrade/downgrade messages from the API errors).
- **Tests:** per feature, happy path plus the error-code UX.

### F9: Launch

- **Deliverables:**
  - SEO: SSR meta and Open Graph for listing and category pages, `sitemap.xml` built from the API, `robots.txt`
  - performance pass (Lighthouse mobile ≥ 85 on home, search and detail)
  - accessibility pass (axe clean)
  - error monitoring (Sentry or Cloudflare), analytics (privacy-friendly)
  - production deploy
  - a legacy retirement plan (redirect the old URLs `/listings/[slug]` → `/l/$slug`)
